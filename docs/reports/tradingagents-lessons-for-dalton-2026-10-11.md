# TradingAgents 对 Dalton 的借鉴价值

调研日期：2026-10-11。阅读版本：[TradingAgents `1394a3f7`](https://github.com/TauricResearch/TradingAgents/tree/1394a3f72aa4393e1a98f51b382434c4b4c2d972)。本报告基于源码及测试审查，未运行其模型调用或投资回测。Dalton 对照基线为 v0.11.11—v0.11.14 的实际运行记录及相应修复。

## 结论

最值得吸收的是三件事：任务在明确的步骤之间交接，中断后接着已完成的步骤工作，研究判断到期后与实际结果核对。它们直接回应 Dalton 当前的问题：大脑提出下一步之后，执行链是否真的继续，已有成果是否被复用，投入是否带来可验证的研究进展。

Dalton 已有原文、事实、模型、预算和研究问题的正式记录。下一步应把这些记录之间的衔接补齐。TradingAgents 的多空讨论和风险角色可以提供参考，但继续增加讨论角色的优先级低于把现有问题读完、把模型算通、把报告交付。

## TradingAgents 实际如何工作

给定一家公司与研究日期，市场、情绪、新闻、基本面分析师分别使用自己的工具和消息历史。所有选中的分析师完成后，多头与空头研究员讨论，研究经理形成投资计划，交易员提出行动，再经风险讨论交给组合经理。分析与到期判断的复盘并行进行。[图构建源码](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/graph/setup.py)

```mermaid
flowchart LR
    A[公司与研究日期] --> B[基本面、新闻、情绪、市场分析]
    B --> C[多空讨论与研究经理]
    C --> D[交易计划]
    D --> E[风险讨论与组合经理]
    E --> F[保存判断]
    F --> G[到期核对结果与复盘]
    G --> E
```

讨论次数由规则控制；分析师的工具调用也有轮数上限。达到上限后要求整理已有发现，防止工具调用一直循环。研究经理、交易员和组合经理使用结构化输出，再渲染为报告。[流程条件](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/graph/conditional_logic.py)、[输出结构](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/agents/schemas.py)

Dalton 的范围更长：一个研究项目持续接收资料，围绕多个问题更新公司档案、季度预测、情景估值与备忘录。因此适合借鉴它的交接和恢复方法，保留 Dalton 已有的持续调度与正式数据记录。

## 值得开发的部分

### 1. 把一次研究拆成可恢复的步骤

TradingAgents 使用 LangGraph 保存节点完成后的状态；恢复时直接接续旧状态。运行身份包含公司、日期、分析师组合、讨论深度、模型配置及组合信息，避免用不匹配的设置接着旧流程运行。测试覆盖“第一步成功、第二步中断、恢复后第一步不再执行”。[运行身份与恢复](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/graph/trading_graph.py)、[中断恢复测试](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tests/test_checkpoint_resume.py)

Dalton 已有内容寻址的任务、正式返回结果和分段暂停。当前缺口发生在这些记录之间：任务已经付费完成，下一步却没有消费；或某一段超时后，整个宏任务长期停在失败记录上。

正在开发的通用规则：

- 成功步骤按原输入、来源、配置及费用凭证复用；恢复只处理尚未完成的步骤。
- 区分模型超时、格式错误、真实证据不足和本地入账失败，各自采用不同处理方式。
- 超时技术恢复绑定原失败步骤，最多一次；原调用的不确定费用继续计入，整个研究任务仍受总预算约束。
- 已经完成读取与独立核验的数字优先本地入账；只有确实缺少答案时才重新调用模型。
- 配置和研究任务版本变化时检查具体受影响的步骤，保留可证明兼容的已付成果。

相关代码：[备忘录暂停与恢复](../../src/dalton_core/investment_memo_quiesce.py)、[已完成数字入账](../../src/dalton_core/document_completed_model_replay.py)、[未执行的已批准恢复入口](../../src/dalton_core/document_unused_recovery_entry.py)。备忘录分组超时恢复已在 v0.11.13 部署，继续观察满足原失败绑定条件的自然续接。微软一项实际数字任务于 13:43 UTC 通过正常调度完成本地入账，两个指标均已保存，新增模型费用为零；14:38 UTC 的正式规划继续引用该结果，并明确采用已核验的 RPO 规模和确认比例。其他任务分别验收。

### 2. 用研究结果衡量推进，任务数量单独统计

TradingAgents 将每次判断记录下来，在观察窗口结束后计算实际回报和相对基准的回报，再形成复盘。回测按公司和日期组合运行，保留失败样本，并把回测记录与日常记忆隔离。[结果核对](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/memory/settlement.py)、[批量评估](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/backtest.py)

对 Dalton，最先需要评估的是研究流程本身。建议把现有只读监控扩成可重复的验收记录：

| 要回答的问题 | 合适的证据 |
| --- | --- |
| 大脑提出的下一步有没有执行？ | 原计划的任务引用、被接收的任务及实际执行结果 |
| 一个数字问题有没有解决？ | 原指标、期间、单位和口径对应的正式答案，及其原文与独立核验 |
| 建模是否推进？ | 新方案是否通过全部历史核对，未来季度需要的单元是否真正可计算 |
| 报告有没有完成？ | 正式报告及独立复核结果；起草进程退出本身不足以证明完成 |
| 是否原地重复？ | 相同输入下的重复失败、无新增证据的重复检索、重复付费次数 |
| 自动恢复是否有效？ | 失败原因是否消除，下游步骤是否消费恢复结果，原费用是否完整保留 |

Dalton 已有[研究周期复盘](../../src/dalton_core/research_cycle_reflection.py)和[研究跟进](../../src/dalton_core/research_followup.py)。优先补充上述关联证据与验收指标，避免再建立一套独立的“完成状态”。现场发现初筛的具体核验失败未进入后续规划，v0.11.14 已部署相应交接。旧任务缺少完整输入绑定时仍标为待核对；新任务是否实际产生、消费有效反馈继续观察。接线与验收方法见[产品核验失败反馈设计](product-validation-feedback-design-2026-10-11.md)。后续自动化应直接读取同一份记录，决定继续执行、等待新证据或请求人的决定。

投资判断的评估另设观察期限：短期股价表现、季度经营结果和长期投资逻辑分别核对。TradingAgents 的复盘提示也明确指出，数日回报可能不足以判断数月的投资逻辑。[复盘提示](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/memory/reflection.py)

### 3. 在历史验收中明确“当时能知道什么”

TradingAgents 的 SEC 路径按申报日期选择当时可见的数据版本，后来的重述从其披露日起才生效。对缺少披露时间的历史报表，它选择不提供，以免把期末日期当成公开日期；复盘记忆也按结果实际揭晓的日期过滤。[SEC 数据选择](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/dataflows/vendors/sec_edgar.py)、[历史报表测试](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tests/test_statement_knowledge_time.py)、[记忆时间过滤](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/memory/log.py)

Dalton 已保留原文版本和来源身份，具备落实这件事的数据基础。建议下一阶段建立统一的历史验收输入：分别保存研究时点、资料公开时点、系统取得时点和结果揭晓时点。每次回放同时检查财报、新闻、事件和复盘记录。只有财报日期正确，不能证明整个研究过程没有看到后来信息。

这项适合在执行衔接稳定后开发；验收至少覆盖后续重述、延迟申报、日期未知、跨时区事件和观察期尚未结束。短期运行修复不会自动变成历史回测能力。

### 4. 给不同研究步骤明确的输入和交接结果

TradingAgents 的并行分析师各自拥有消息历史，只返回负责的报告字段；下游在全部报告返回后启动。这种结构有助于减少上下文互相污染，并明确下一步需要什么。[并行分析实现](https://github.com/TauricResearch/TradingAgents/blob/1394a3f72aa4393e1a98f51b382434c4b4c2d972/tradingagents/graph/setup.py)

Dalton 更适合按问题分配工作：一个步骤回答某个指标，另一个步骤核验该答案，再由建模或起草步骤消费。交接结果应包括目标、来源版本、已完成部分、未完成原因及允许的下一步。当前正在补的建模字段修复和完整收入分组输入属于这一方向：让模型选择有出处的口径，验证器检查明确的字段，失败原因再进入规划。

增加并发前先证明步骤彼此独立，并把所有步骤的费用计入同一研究预算。并发带来的价值要用实际完成时间和每个已解决问题的费用衡量。

## 开发顺序与验收

1. **先完成通用恢复与交接。** 当前正在处理备忘录分组超时、已批准未启动的阅读、不同财务口径的身份冲突，以及建模输入遗漏。每项修复都以错误类别、数据结构和来源身份判断，实际公司的失败记录仅作为回放样本。
2. **补齐研究推进验收。** 对每个现有研究问题记录“计划—执行—核验—正式产出—下游采用”，同时统计重复费用和等待原因；农业以外的九家公司作为当前观察集，测试另用不同公司的合成结构。
3. **再建设按时点的评估与跨公司经验复用。** 从已有财报预测与实际结果的核对开始，逐步扩展到观点和事件；日期不明确、观察期未结束的样本单独保留。

通用验收要求：换公司名称或股票代码后规则仍成立；同口径和不同口径能够区分；部分成功后恢复不会重复购买成功步骤；配置变化不会清空历史费用；资料缺失保持具体缺项；格式修复不能修改无关金额、出处或公式。正式结果出现后，再检查后续研究是否实际使用。

EPAM 的恢复取得三项答案中的两项，但旧规划摘要仍笼统写作“正在处理”：旧代码只投影整组完成的结果，部分完成的答案在进入摘要前就被过滤掉。v0.11.13 已将核验通过的已完成子集连同“部分完成”和剩余目标送入规划。15:31 UTC 的真实规划输入已包含交付人员 56,600、利用率 76.8% 及各自来源，剩余成本占比继续保留。执行成功、结果进入规划、后续交付采用，分别检查。初筛核验缺因反馈已在 v0.11.14 部署，等待新任务的实际交接验收。

当前线上健康检查、逐公司修复与这项调研并行执行，进展见[公司研究推进修复记录](research-execution-recovery-2026-10-11.md)。本报告没有引入 TradingAgents 的运行依赖，也没有复制其实现；后续若直接采用代码，按仓库 Apache-2.0 许可保留相应声明。
