# P10a：任务开始按研究手册的阶段走，两条 lane 跟着缺口走

*2026-09-07*  ·  基线：[愿景 v1.1](vision-and-next-phase-v1.1-2026-09-07.md)

## 这一片回答的问题

Phase 9 把团队方法论写成了合同：每家公司走 Initial Screen → 深度认知门 →
行业模型 → 公司模型 → Investment Memo → 持续覆盖，每个阶段有必读、必交和出口门。
P9d 让"搜 → 取 → 读 → 入库 Claim"全自动。两者之间没有接口：live 的阶段账本
是 0 行，而两条 lane 都按行的新旧挑下一份文档。

后果在数据里看得见：15 份电话会纪要全属于 EPAM，18 份券商研报全属于 CTSH，
而优先级 P0 的 ACN 两样都没有——每天 30 次受治理的 AlphaEngine 调用，
被先被发现的公司占满了。owner 在新驾驶舱上看到的"子任务"因此是资料计数，
而不是他理解的"建立 ACN 的 Initial Screen"。

## 做了什么

**进入第一个阶段。** `mission_stage` 每跳给还没有阶段记录的公司写一条
`initial_screen entered`，actor 是任务自己的 automation principal，
mission v7 早就授予了 `stage_record`。这里不过任何门；过门要等交付物（P10c）。

**把必读清单变成能数的四项。** Playbook 的 Initial Screen required_readings
（"过去 4 个季度财报与电话会、最新年报或招股书、近 6 个月多空券商观点"）
翻译成四项计数：季度财报数字、电话会纪要、年报正文、券商观点。一份文档算进
哪一项，由**找到它的发现规格**决定——发现记录里本来就存着 spec_ref，而规格自带
`document_type`，所以不需要读正文去猜类型，也不新增任何权威。每项的状态是
已齐 / 部分 / 缺 / 没有通道 / 来源未接入，并带一句人话。

**两条 lane 跟着缺口走。** `acquisition_needs` 把 (公司, 规格) 按任务自己的
bootstrap 优先级和手册的阅读顺序排出来，`next_discovered_document` 新增
`preferred_needs`：匹配第一项缺口的文档排在匹配第二项之前，都排在没人需要的
文档之前。抽取子进程同样改为按 (公司优先级, 原文类型, 时间) 读——管理层自己的话
排在别人对它的转述之前。年龄只做最后的 tie-break。

**驾驶舱的子任务变成"公司 × 阶段"。** 每家公司显示当前阶段与状态、四项清单的
勾选情况、还差什么，进度条按清单完成度而不是文档数。

## 部署时发现并修掉的两件事

**排序被一个错属性静默关掉。** 第一次部署后阶段账本正常写入，但获取 lane 仍然
挑 EPAM 的文档。原因是协调器里调了 `self.load_plan()`——那是 launcher 的方法，
协调器持有的是 `self.plan`；`except Exception: return []` 把它咽了下去，
结果"没有缺口"和"算缺口时崩了"看起来一模一样。现在这段把原因写进 tick 报告
（`stage_order: {count, first, error}`），live 一跳就指出了
`AttributeError`。修好后 live 报告 8 项缺口、第一项是 ACN 的电话会纪要，
它选中的正是 ACN 的那份文档，只被当日已用满的 30 次额度挡住。测试补上了这条。

**年报那一项不是"少一条搜索规格"。** 查 AlphaEngine 自己的文档类型目录后确认：
它只有会议纪要与各类研报，**没有年报或 10-K**。所以这一项的来源改成
`source:sec-edgar`，说法也改成实话——"还没有获取 10-K 正文的通道；现在只从 SEC
取了财报数字"。这是 P10 后续切片要建的一条 lane，不是一条查询。

## 验证

- 15 项新测试：清单按发现规格计数（已取 / 待取 / 失败 / 已读分开）、未接入的来源
  报"拿不到"而不是"缺"、季度财报只数定量 Claim 的不同期间、每家公司只进入一次
  第一阶段且用任务自己的 principal、没有 `stage_record` 授权时如实报告而不是抛错、
  automation 仍然过不了人审的门、缺口排序把 P0 公司和手册阅读顺序排在前面、
  获取 lane 在有缺口时选缺口文档而在没有时回到最旧、协调器如实报告它的排序。
- live：五家公司阶段账本非空（automation 写入，ACN 在前）；驾驶舱按公司显示
  阶段与四项清单；获取 lane 报告 8 项缺口、第一项 ACN 电话会纪要；抽取按新顺序
  继续运行（一轮读 4 段、关闭 4 份文档）。
- 全套 1214 项测试，只余两项已知的 macOS 路径失败与一项单跑即过的 node broker 用例。

## 顺带记录的一次故障

连续第三次部署时，一个抽取子进程在 scheduler 上撞到 `database is locked`
（5 秒 busy timeout，多进程同时提交）。此前所有抽取运行都没有出现过，之后几轮
也全部成功，判定为部署竞态。没有改那个 5 秒——全仓统一约定，为一次竞态调高它是
掩盖而不是修复。若在非部署时段复现，再按真实的并发问题处理。

## 这一片没做

出口门自评与 Initial Screen 文档（P10c，需要交付物 authority）；误归属 Claim 的
挑战与退役（P10b）；SEC 10-K 正文获取通道；发现 lane 的缺口驱动查询（现在只有
获取与阅读按缺口排序，搜索仍按固定间隔轮询）。
