# 大版本起点：研究流程为什么反复卡住

记录日期：2026-10-13。依据当前代码、三套研究环境的实际任务与正式结果，以及三名并行开发代理的复核。

## 开发方向

本轮已经确认共性的架构问题。后续主线转为统一任务执行、研究反馈和事实输入，不再以继续增加各种错误的专用恢复入口为主要办法。

按用户要求，先收拢本轮代码与文档，通过合并检查后进入 main，再建立独立大版本分支。本轮 main 合并保存开发基线，不表示所有研究问题已经解决，也不自动切换线上版本。线上仍是 v0.11.44，源码 `dc0d9c47`。

## 已确认的问题

| 问题 | 实际表现与代码依据 | 大版本要改变的边界 |
| --- | --- | --- |
| 研究任务、执行设置和版本身份耦合 | 模型请求身份包括修正次数；子进程票据绑定配置。调整设置或升级后，需要专用的 rebind、replay、maintenance 规则才能续接。[模型请求](../../src/dalton_core/company_model_cli.py)、[子进程票据](../../src/dalton_core/mission_document_research_launcher.py) | 分开记录研究任务、输入修订和执行尝试。当前模型、预算和运行版本决定下一次怎么执行，不自动否定已有有效回答 |
| 任务状态由多个地方分别推断 | Scheduler 已结束、数字结果部分完成、holds 仍要求恢复可以同时出现。农业八条待恢复记录中，包含数字写入失败、真实输出错误和已有部分结果等不同情况。[任务协调](../../src/dalton_core/mission_document_research_lane.py)、[完成判断](../../src/dalton_core/document_numeric_completion.py)、[待办](../../src/dalton_core/needs_human.py) | 建立统一任务生命周期。计划、调度、进度和人工待办从同一状态读取；执行尝试失败不直接等于研究任务需要人工决策 |
| 保存的规划没有统一、可执行的动作凭据 | FMC 的 EPS 附注已被选入规划，但原选项别名与保存后的完整目标不一致，执行端拒绝；局部修复已保存。[规划交接](../../src/dalton_core/planner_note_options.py)、[读取准入](../../src/dalton_core/mission_document_research.py) | 规划先产生动作提议，经过同一入口解析、检查能力与前置条件后形成任务。接纳、排队、执行和结果都返回同一个动作记录 |
| 全局状态变化反复唤醒已不可执行的同一问题 | Hyperscaler 在 14:37–15:02 UTC 的六份规划全部正式保存，其中四份各产生一条新任务，两份没有产生新任务；后两份再次提出已接纳过的 MSFT 目标。其他公司的反馈变化也会唤醒整份规划 | 按研究问题和有效输入变化安排工作。规划看到已有后继任务及其状态；改写指标名或期间文字不能构成新操作 |
| 显示文字参与事实身份，且身份信息不完整 | `_period_key` 删除非英文字符。CF 的两个中文期间表述落在同一旧 Figure ID 上，写入认定重复，后续读取却按原字符串找不到。旧身份也未完整包含单位、数量级与口径。[事实写入](../../src/dalton_core/coverage_mission.py)、[数字执行](../../src/dalton_core/directed_numeric_executor.py) | 期间、币种、单位、数量级、维度和申报口径采用结构化字段。显示语言独立；事实修订、不同测量和同事实的不同引用各有明确关系 |
| 原文和正式事实进入模型的通道分散 | XBRL 报表、Figure、财务附注、经营指标分别进入不同上下文。材料找到或事实正式入库，不代表模型一定能使用。CF 的原始建模回答、AGCO/ADM 的已保存模型缺项需要不同衔接 | 统一事实读取接口与缺项描述。模型引用经过核验的事实身份，缺项统一产生可获取、可验证、可完成的资料需求 |
| 校验和修正规则重复维护 | 实际输入支持新来源字段，部分修正入口仍检查静态 `OUTPUT_SCHEMA`。一个合法字段会使另一个修正入口失效。[模型规格](../../src/dalton_core/company_model_spec.py)、[联合诊断](../../src/dalton_core/model_spec_joint_field_diagnostics.py) | 同一模型编译与校验入口生成输入规则、完整诊断和允许的修正范围；旧版本通过显式读取适配器核对 |
| 来源能力与业务要求没有完整对应 | NTR 有外国发行人年报数字，但缺正式季度资料；6-K 原件、附件、季度识别、单位和报表入账尚未形成完整通道 | 资料能力描述获取方式、可读格式、期间覆盖和可产出的事实类型。不能满足要求时，任务生成具体依赖，不反复运行不具备能力的步骤 |

这些结论不意味着出处核验、独立复核、财务勾稽或费用记录应被删掉。应统一它们的调用与状态边界，避免每个流程重新实现一套身份、恢复和完成判断。

## LLM 应放在哪里

LLM 适合解释原文口径、选择研究方法、提出公式和处理有明确证据的修正。单纯在每个失败后再加一轮调用，会让执行衔接错误继续消耗预算。

建议的新流程是：程序汇总结构化诊断，区分缺材料、执行故障、格式错误与研究判断；只有确实需要判断时，模型接收完整诊断、已有证据和允许的动作。修正后仍通过统一校验。已完成的读取、起草和核验按有效输入复用，新增调用单独记入当前任务的累计费用。

同一输入、同一错误且没有新信息时不重复购买相同回答。系统故障进入运维处理；只有研究范围、来源权限、追加预算或分析判断确实需要用户决定时，才进入分析师待办。

## 优先改造的完整流程

先选一条贯穿全程的研究任务，同时覆盖申报财务数字和经营指标：

1. 研究问题产生结构化需求，包括对象、指标、期间、口径和回答标准。
2. 能力检查生成明确的获取、读取、核验和建模依赖；已有有效成果直接复用。
3. 原文经过核验形成统一事实；每条事实保留原文位置、原始数值、精度与解释口径。
4. 模型通过统一接口引用事实，完整校验一次汇总所有可诊断的问题。
5. 必要的有界 LLM 修正完成后，从失败步骤续接，研究进度和页面使用同一状态。

使用 CF 的三期量价、另一家公司已申报收入或现金流，以及 NTR 的不同披露格式作不同输入的验收。实现不包含股票代码分支，也不自动替公司选择经济公式。

## 保留与迁移

保留原始文件、正式研究版本、已付费模型回答、调用及结算账本、权限检查和财务校验。新系统通过明确的旧版读取适配器引用这些记录，不改写历史事实或费用。

新任务和旧任务先并行只读比较，再逐步接管执行。同一研究步骤只能有一个写入执行者。切换应覆盖在途调用、已回答但未入库、部分完成、预算暂缺和来源尚未发布等状态。

现有 scheduler、writer、broker 与 ledger 提供了可保留的基础；本记录没有决定引入另一套调度框架或重写所有模块。

## 大版本验收

- 调整模型顺序、token 上限或时限、升级及重启后，同一有效回答仍被复用。
- 已接纳的动作必有可查的任务、结果或具体依赖，不能只保存一段“下一步建议”。
- 系统错误、资料缺失和分析师决策在状态与页面上保持一致。
- 同一事实的中文、英文和展示格式变化不会生成冲突身份；真实期间或口径不同不会被合并。
- 多种申报格式与不同公司的事实通过同一模型输入接口，仍保留各自来源与适用范围。
- 模拟中断、未知送达、部分完成和预算等待后，任务能有界续接，历史费用和成果保持完整。
- 逐项比较正式研究产出及任务完成率，不能以进程健康、模型返回或局部测试数量代替验收。
